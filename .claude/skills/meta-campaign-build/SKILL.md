# Meta campaign build

**Read first.** Read `memory/maps/build.md` and every `memory/learnings/meta-platform/` note it lists before any create, update or activate; the rules below summarise them, and the notes win. Then `memory/state/current.md`, the campaign note in `memory/campaigns/` and the flight note in `memory/flights/` for the work at hand (vault contract `memory/README.md`, "who reads what").

**Output:** PAUSED objects in the ad account; every id, hash and video id in the flight's plan file (`plans/`), the campaign note and the flight note's creatives table, and the campaigns table of `memory/state/current.md`; upload ledgers in `creatives/uploads/`. **Language:** files in English; ad copy in the ad's language as written in the plan; anything said in chat in the chat language from `config/operator.md`.

## Account constants (read, never hard-code)
From `config/accounts.md`: `meta_ad_account_id`, `business_portfolio_id`, `page_id` (and the duplicate Pages to avoid), `instagram_account_id` (may be none), `pixel_id`, `lead_form_ids`, `lead_delivery` and `lead_webhook_url` (none by default), `whatsapp_number_names`, `currency` and its minor unit (budgets are sent in minor units), `min_daily_budget`, the attribution parameters (`ref`, `utm_*`), the conversion domain (the host of the website in `config/company.md`). From `config/product.md`: the funnels and the destination pages. From `config/claims.md`: the special ad category per market and the forbidden words. From `config/brand.md`: the languages, their direction, the AI-imagery disclosure rule. From `config/operator.md`: the timezone, the exact phrasing of a go and who answers leads (the replies row). From `config/goals.md`: the hard caps (daily, weekly, monthly, per campaign) and the target cost per result per funnel.

**Draft mode depends on the account.** On some accounts every write creates a real object in status PAUSED (no draft staging; `object_state: draft` reads answer "being gradually rolled out"): paused objects spend nothing, edits to them are ordinary live edits, and only `ads_activate_entity` makes anything run. On others, writes are staged as Ads Manager DRAFTS (the draft-mode notes in `memory/learnings/meta-platform/`). Record which one this account is on the first build, as a learning note under `memory/learnings/` linked from `memory/maps/build.md` and a line in the account facts of `memory/state/current.md`, and follow that branch.

There is no lead-form tool (forms are built in Meta Business Suite; the id is read in its forms library) and no targeting search (ids from the account's own earlier ad sets or the Ads Manager editor).

**Gate before any build:** first, the `meta-ads` tools (`mcp__meta-ads__*`) are loaded in this session; the server is declared in the repository's `.mcp.json`. When they are missing, stop and say so: the fix is `health` check 1 (approve the server in `/mcp`, the Owner logs in, a new session). Then `ads_get_ad_accounts` and `ads_get_user_pages` must show the account and the Page named in `config/accounts.md` and `memory/state/current.md`. If they show other assets only, stop and report the blocker (wrong login).

## Non-negotiables
1. **Money gate.** Never call `ads_activate_entity`, raise a budget, extend a schedule or create an experiment that changes delivery without an explicit go from the Owner in the same message (phrased as in `config/operator.md`). Before asking, state the daily spend and the cap for the schedule (Meta lets a daily budget spend up to 7× per Sunday–Saturday week, prorated; state the worst case) and the cap in `config/goals.md` it stays under (rule 10). Activation runs in the main session only; `media-buyer` never activates.
2. **Create, don't update, structure.** Set `targeting`, budgets, schedule, optimization and `special_ad_categories` at creation. **Never update `targeting` on a draft ad set** with `ads_update_entity`: the draft vanishes from the Ads Manager table and its editor hangs while the MCP still reports VALIDATED. Scalar updates (name, start_time, status) are safe. To change a draft's targeting, the Owner discards the draft and the harness recreates it. (On an account without draft staging, targeting edits to PAUSED real objects are ordinary live edits.)
3. **Inline creatives only.** Build ads with `object_story_spec` inside `ads_create_ad`. Never use `ads_create_creative` with a headline (the tool adds the deprecated `call_to_action.value.link_title`; Ads Manager rejects the ad with #1815589 even though the MCP says VALIDATED and the preview renders).
4. **No `standard_enhancements`** (deprecated, publisher error 3858504, not caught by the MCP validator). Opt out of the eleven individual features in `degrees_of_freedom_spec.creative_features_spec`: image_brightness_and_contrast, enhance_cta, text_optimizations, image_templates, inline_comment, image_touchups, image_uncrop, image_background_gen, add_text_overlay, site_extensions, video_auto_crop.
5. **AI self-disclosure.** Whenever any asset is generated or altered, add at the creative root `"generative_asset_spec":{"transparency_metadata":{"self_disclosure":{"enroll_status":"OPT_IN"}}}` (an object; the bare string `"OPT_IN"` is rejected with code 100 "must be a JSON object"), and apply the visible disclosure rule in `config/brand.md`.
6. **Verify after every publish.** `ads_activate_entity` returns PUBLISHING even when the publisher rejects objects; nothing reports it back. Re-read live (`ads_get_ad_entities`, level ad/adset) and, on a draft account, the draft; run `ads_get_errors`; Ads Manager → "Review and publish" → details shows what stayed behind. Publishing only the listed `object_ids` leaves the rest in the draft.
7. **Special ad category.** Declare at campaign creation the category `config/claims.md` sets for the market and `config/audiences.md` sets for the audience (NONE / HOUSING / CREDIT / EMPLOYMENT / ISSUES_ELECTIONS_POLITICS). Where Meta applies a category in a geo and the config is unsure, confirm in Ads Manager before building; when in doubt declare it (it restricts age, gender, postcode and lookalike targeting). A B2B service ad that does not offer the regulated thing is not in the category.
8. **Compliance gate.** Copy and creatives have passed `compliance-check`. None of the forbidden words or claims in `config/claims.md`; lines that need clearance only once cleared; no consent or notice wording of our own (quote the ids in `config/claims.md`).
9. **Creatives are immutable.** `ads_update_entity` refuses `creative` and `creative_id`, so a one-word change to a primary text means new ads (`ads_create_ad`, same media hashes) plus `status: DELETED` on the old ones (which sticks on PAUSED real objects; read back DELETED). Record the old ids and strings in the plan first. A new creative is a new ad, never an edit.
10. **Caps from `config/goals.md`.** Before proposing any daily budget, read its hard caps (the caps table: daily, weekly, monthly, per campaign, in the account currency). A proposed daily budget is never above the daily cap; the sum of the daily budgets of everything live plus the proposal is never above the daily cap; that sum ×7 (Meta's weekly ceiling for daily budgets) is held against the weekly cap, and the flight's worst case against the monthly cap and the campaign's own cap. Budgets go to Meta in the minor unit: compare in one unit. When a proposal would cross a cap, say so and propose a lower budget, a shorter schedule or a reallocation; only the Owner changes a cap, in `config/goals.md`. The spend statement before a go quotes the cap it stays under, for example "60/day on two ad sets, worst case 420 this week, under the weekly cap of 500". Meta may spend more than a daily budget on a single day within the weekly ceiling, so say so when the budgets sit close to the daily cap. When `config/goals.md` is missing or holds placeholders, the spend statement says "no caps set" and recommends `/setup` round (i) before the go.

## Standard build sequence
1. Read `memory/state/current.md`, the campaign and flight notes, and the relevant plan. Confirm the Page, the pixel, image hashes or video ids (`ads_get_ad_images`, `ads_get_ad_videos`) and the copy to use. New files: upload them first (see "Media uploads") and record the hashes and ids in the plan's media table before any ad is created. Media the plan marks as superseded never go in an ad.
2. `ads_create_campaign`: objective per funnel (below), AUCTION, `special_ad_categories` per rule 7, no campaign budget (ABO) unless the Owner asked for CBO. Name `<YYYY-MM>-<objective>-<market>_<audience>_<lang>-<variant>`, for example `2026-11-LEADS-XX_Buyers_EN-SignUp_A`.
3. `ads_create_ad_set` per arm: `daily_budget` in the currency's minor units (not below `min_daily_budget`, within the caps of rule 10), ISO start/end with the UTC offset of the account timezone at that date, `targeting` with geo + language + signals as suggestions, `location_types` set explicitly to `["home","recent"]` (omitting it stores the removed `["home"]`, which makes the editor show "Your audience contains a location targeting option that has been removed" and stop re-estimating; click-to-WhatsApp sets keep `frequently_in`), `targeting_as_signal` 3 where Advantage+ audience is used (under Advantage+ audience, locations, languages, minimum age and excluded custom audiences are controls and hold; `age_max` is only a suggestion), `promoted_object` per objective, destination WEBSITE, lead form or WhatsApp.
4. `ads_create_ad` per creative: name `CREATIVE_<number> | <arm>` (the creative's fixed flight number), inline creative (link with `ref` and UTMs, message, name = headline, `image_hash` or `video_id`, `call_to_action` with the same link), the eleven feature opt-outs (rule 4), OPT_IN when anything is generated (rule 5), `tracking_specs` `[{"action.type":["offsite_conversion"],"fb_pixel":["<pixel_id>"]}]` and `conversion_domain` the company's domain (both left out when `config/accounts.md` records no pixel and no website). Click-to-WhatsApp ads: `page_welcome_message` (see below). A video ad: `object_story_spec.video_data` with `video_id`, `image_hash` (the thumbnail), `title`, `message` and the same `call_to_action` and link as the still ad; the video must read `ready` in `ads_get_ad_videos` before the create.
5. Read the objects back live by id (`ads_get_ad_entities` with `object_ids`; on a no-draft account they are PAUSED live objects). Status PAUSED, the budget, schedule and targeting as sent. Run `ads_get_errors`.
6. Check rendering: `ads_get_ad_preview` for every ad of the set → one `creatives/tools/ad-shots.sh` call with all the URLs → images to the Owner (never a browser pane). In Ads Manager (when the Owner asks for a browser check) the ad sets and ads tables show rows with thumbnails; allow about 20 s for MCP-made objects to render. When a language in `config/brand.md` is RTL, check the preview reads right-to-left with no clipped currency sign or digits. Read the ad set's audience panel before trusting its spec.
7. Record every id the same turn: in the campaign note (`## Current state` rewritten from step 5's read with `as_of`, a `## Log` line with the ids in backticks; a new campaign gets its note from `memory/templates/campaign.md`), in the flight note's creatives table (number, name, format, hash or video id, status), in the campaigns table of `memory/state/current.md`, and in the plan file; a line in today's session note `memory/sessions/YYYY-MM/YYYY-MM-DD.md`; `checklist.md` if a gate moved. Not only the plan, never only chat. When this skill runs inside a sub-agent (`media-buyer`), the agent writes the plan file and its handoff only; the main session writes the campaign, flight, state and session notes from that handoff in the same turn it receives it (one writer).
8. Ask for the publish go with the spend statement. On go: `ads_activate_entity` with `object_ids` = all ids to run (ads, ad sets, campaign). A sequence that works: a scalar `start_time` edit on the ad set, then activate the ads, the ad set and the campaign; ads still `IN_PROCESS` at activation go active once review passes (minutes), and a set whose `start_time` is ahead reads `scheduled` until it ticks. Then verify (rule 6) and rewrite the campaign note's `## Current state` from the live read, with a `## Log` line. Then append one row to `memory/money/go-log.md` in the same turn (shape in `memory/maps/close.md`): date, time with the timezone of `config/operator.md`, channel (chat / WhatsApp quoted / email quoted), the Owner's words quoted exactly, the ids activated, the daily budget and the cap from the spend statement the go answered, the schedule end, who executed; set the note's `as_of`. A go that was refused or not executed gets a row too.
9. For an A/B test: create the experiment after publish with `ads_experiment_abtest_create_test` (cells = ad set ids, start = tomorrow in the account timezone, end = schedule end, primary KPI per funnel), on the Owner's go.

## The first flight: a still and a video in one ad set
The first flight plan (`/setup` step 6) names one still and one silent video for the first funnel; both go into the one ad set of the first campaign, PAUSED, as two ads with the same copy, link and `ref`:
- `CREATIVE_01 | <arm>`: a single-image ad, `link_data` with the still's `image_hash`.
- `CREATIVE_V01 | <arm>`: a video ad, `video_data` with the video's `video_id` and `image_hash` = the still's hash as the thumbnail (the video's last frame is the still; `creative-production` §4a), the same `title`, `message` and `call_to_action` (for click-to-WhatsApp the same `page_welcome_message` at the `object_story_spec` level). `ads_get_ad_videos` must show the video `ready` before the create; a video still processing fails the ad without a useful error.
- Numbers: the video takes the flight's next creative number as `V<NN>`; both rows go into the flight note's creatives table and the plan's media table with the date, the hash, the video id and the thumbnail hash.
- Step 6 for both: `ads_get_ad_preview` for each ad, one `ad-shots.sh` call with both URLs, both images to the Owner (the video preview shows the thumbnail frame with the play control); `ads_get_errors` empty for both before the numbered recap.

Without the HyperFrames plugin the first flight ships the still alone and the plan's video row reads "bring your own file"; the video ad is added when the file arrives, as a new ad in the same set.

## Lead-form ads
- The form is built in Meta Business Suite (there is no lead-form tool); its id comes from Business Suite's forms library and goes into `lead_form_ids` in `config/accounts.md` and the plan. The instant-form buttons are in the table under "Objectives and events per funnel type".
- **Lead delivery:** Leads Center by default, per `lead_delivery` in `config/accounts.md` (email notifications, a CSV download from the forms library or a CRM integration are the other routes Meta offers). Before the first lead ad runs, the Owner opens Leads Center once and confirms that new-lead notifications reach the person named in `config/operator.md` under replies; until then the `checklist.md` row stays open and the spend statement names it as a gate.
- The webhook registration step (the developer app's `leadgen` subscription carrying every running form id) applies only when `config/accounts.md` holds a `lead_webhook_url`; otherwise it is n/a.
- The harness never reads lead rows (no tool reads them, and they are personal data): lead counts come from the ad set's results.

## Click-to-WhatsApp ads
- Pass `page_welcome_message` at the `object_story_spec` level of the inline creative (a JSON string, VISUAL_EDITOR v2, `autofill_message`), in the language of the ad's audience from `config/brand.md` / `config/audiences.md`; inside `link_data` the MCP returns a bare INTERNAL error. Without it the chat opens with Meta's English default. Ice-breakers: up to four, 80 characters each.
- The MCP cannot set or change an ad set's WhatsApp number (`promoted_object` updates return INTERNAL). A number is connected in Page settings → Linked accounts → WhatsApp, only once it lives on the WhatsApp Business app, and selected per ad set in the editor: the Owner's click. A second number must not become the Page's primary (sets without an explicit choice follow the primary). Number names only, from `config/accounts.md`.
- Detailed targeting is not available for click-to-WhatsApp; Advantage+ detailed targeting is applied to conversation-optimised sets.

## Custom audiences
Audiences are created **only from a ladder plan** (`plans/<YYYY-MM-DD>-audience-ladder.md`, written by `audience-research`, "The retargeting ladder, built"), one call per row whose status is `planned`; never from a request in chat alone, and never a row marked `blocked` or `n/a`. Creating a website, engagement or lookalike audience spends nothing and needs no go; putting it into an ad set that runs follows the money gate (rule 1).

**Before a create:** `ads_get_ad_account_custom_audiences` (nothing with the same rule exists already); the ids come from `config/accounts.md` (`meta_ad_account_id`, `pixel_id`, `page_id`, `instagram_account_id`, `lead_form_ids`); the name is the plan row's (`<company short>_<source>_<window>_<date>`).

**`ads_create_custom_audience` parameters:** `ad_account_id`, `name`, `subtype` (`CUSTOM` | `WEBSITE` | `ENGAGEMENT` | `MOBILE_APP` | `LOOKALIKE`), `description` (the plan file and row number), `rule` (WEBSITE, ENGAGEMENT, MOBILE_APP), `prefill` (true fills the audience from past activity within the retention), `retention_days` and `customer_file_source` (CUSTOM only), `origin_audience_id` and `lookalike_ratio` (LOOKALIKE only), `audience_labels` (optional, for example the plan's date).

**`rule` is a JSON-encoded string**, not an object: build the object, then send it serialised (every inner quote escaped). Retention is in seconds: 30 d `2592000`, 90 d `7776000`, 180 d `15552000`, 365 d `31536000`.

All visitors, 30 days (template `ALL_VISITORS`; an empty `i_contains` matches every URL):
```json
{"ad_account_id":"<meta_ad_account_id>","name":"<short>_web-all_30d_<YYYY-MM-DD>","subtype":"WEBSITE","description":"plans/<date>-audience-ladder.md row 1","prefill":true,
 "rule":"{\"inclusions\":{\"operator\":\"or\",\"rules\":[{\"event_sources\":[{\"type\":\"pixel\",\"id\":\"<pixel_id>\"}],\"retention_seconds\":2592000,\"filter\":{\"operator\":\"and\",\"filters\":[{\"field\":\"url\",\"operator\":\"i_contains\",\"value\":\"\"}]},\"template\":\"ALL_VISITORS\"}]}}"}
```
The other website rungs change only the inner rule (shown here before encoding):
- Conversion-page visitors: `"template":"VISITORS_BY_URL"` with `{"field":"url","operator":"i_contains","value":"<the conversion page's path>"}`.
- Converters: the filter `{"field":"event","operator":"eq","value":"<the funnel's event, e.g. Lead>"}`, the event name exactly as the pixel sends it (`config/accounts.md`, pixel-events row; confirm with `ads_pixel_event_read`).
- Top time spenders: `"template":"TOP_TIME_SPENDERS"` with an `aggregation` block whose fields follow the tool's schema at build time.
- Engagement rungs: `subtype` `ENGAGEMENT` and `event_sources` of type `page` (the Page id), `ig_business` (the Instagram account id), `lead` or `ig_lead_generation` (instant forms; these need `owner_id`, the Page, placed as the tool's schema places it); `retention_seconds` 0 means current followers only. Which engagement (all engagers, opened a form, submitted a form) is selected by the filter values in the tool's schema; take them from the schema or `ads_get_field_context`, never from memory. A video-viewer source is used only when the schema lists one.

Lookalike (geography is automatic from where the ad set runs; never send or ask for a country):
```json
{"ad_account_id":"<meta_ad_account_id>","name":"<short>_lal1-<source token>_na_<YYYY-MM-DD>","subtype":"LOOKALIKE","origin_audience_id":"<source audience id>","lookalike_ratio":0.01}
```
`lookalike_ratio` is 0.01–0.20 (1 % = 0.01, 3 % = 0.03). Only when the source has reached the plan's minimum size, and never for a campaign in a special ad category (the table in `audience-research`).

**Rules:**
- **Record the same turn.** Read the new audience back with `ads_get_custom_audience` (subtype, rule, retention, `approximate_count`, `delivery_status`) and write its id into the plan row (status `built`) and into `memory/audiences/<name>.md` (from `memory/templates/audience.md`: `ids`, `size` with `as_of` and `source` = the live read, `used_in`). A sub-agent (`media-buyer`) writes the plan row and its handoff; the main session writes the audience note.
- **A lookalike is not usable until Meta reports it ready.** It populates over hours. Until `ads_get_custom_audience` shows a ready delivery status and a size, no ad set is built on it; the plan row stays `built`, then `ready`.
- **In ad sets:** included and excluded audiences go into the ad set's `targeting` at creation (the field names per `ads_get_field_context`; rule 2 applies, so on a draft account they are never added later by a targeting update). The exclusions are the plan's (converters out of prospecting; each rung excludes the rung above).
- **Changes:** `ads_update_custom_audience` for the name, description or labels; a different rule or retention is a new audience with a new name and a new plan row.
- **Customer lists (`CUSTOM` + `ads_update_custom_audience_users`):** never without the Owner's ruling recorded in `config/claims.md` ("Custom audiences from company lists") that the named list may be used; that ruling also names who uploads it. Default: the Owner uploads the list in Ads Manager and the harness reads the id back. When the ruling names the tool, the rows come from a file the Owner places outside this repository for that one call, hashed per the tool's schema (`schema`, `customer_consent`), never echoed to chat and never written to a plan, report, note or log; only the count is recorded. Rows are never stored in this repository.
- **Deletes are the Owner's.** `ads_delete_custom_audience` runs only from the main session on the Owner's explicit word in chat, after `ads_get_custom_audience_adsets` shows no live ad set uses it (`media-buyer` cannot call it). The plan row becomes `deleted` with the date.

## Catalog and Advantage+ shopping campaigns
For companies that sell products from a feed: when `config/product.md` names a product feed (Shopify, WooCommerce, Wix, or a CSV or XML URL) or the `catalog-ads` skill's intake recorded one. Every catalog tool takes its parameters per the tool's schema at build time; read the schema (and `ads_get_field_context`) before the first call and never invent a field. `ads_catalog_list_guidance` returns Meta's own catalog guidance; read it once per new catalog.

**Order of work** (each step's ids go into the plan and `memory/state/current.md` account facts the same turn):
1. **Catalog.** `ads_catalog_get_businesses` (the portfolio in `config/accounts.md`) → `ads_catalog_list_catalogs`; reuse an existing catalog (a store platform's Meta integration usually created one: `ads_catalog_list_partner_integrations`, `ads_catalog_get_data_sources`). Only when none exists, `ads_catalog_create`; `ads_catalog_update_catalog` for its name or settings.
2. **Feed.** `ads_catalog_list_product_feeds`; when the store platform's integration already syncs products, use that feed and add none. Otherwise `ads_catalog_create_product_feed` with a scheduled fetch of the feed URL (daily at least); `ads_catalog_update_product_feed` for changes. **A feed URL's credentials (a password, or a token in the URL) are the Owner's:** the Owner enters them in Commerce Manager, the harness records the credential's name only and never opens, prints or pastes a value. A one-off fetch: `ads_catalog_create_product_feed_upload_session`; its result: `ads_catalog_get_product_feed_upload_sessions`. Field fixes (currency, availability, a mapped column): `ads_catalog_get_feed_rules`, `ads_catalog_create_feed_rule`. Single items: `ads_catalog_list_products`, `ads_catalog_product_create`, `ads_catalog_update_product` (only for a catalog without a feed; with a feed, fix the source, since the next fetch may overwrite a hand edit).
3. **Diagnostics clean.** `ads_catalog_get_diagnostics` shows no MUST_FIX issue and `ads_catalog_get_dynamic_ads_health` is healthy; spot-check `ads_catalog_list_products` against the live site (price, currency, availability, image, link in the destination language). Nothing below runs on a catalog with a MUST_FIX issue.
4. **Event source.** `ads_catalog_event_source_get` → `ads_catalog_event_source_connect` with the pixel in `config/accounts.md` → `ads_catalog_event_source_get_health` (ViewContent, AddToCart and Purchase arrive with content ids that match the catalog) and `ads_catalog_event_source_get_recommendations`; `ads_catalog_event_source_get_catalogs` lists what a pixel is already connected to. Run `signals-audit` on the same events. A wrong link is undone with `ads_catalog_event_source_disconnect`.
5. **Product sets.** `ads_catalog_get_suggested_filter` → `ads_catalog_create_product_set` (for example all in-stock products, a category, best sellers) → `ads_catalog_list_product_sets` with each set's product count; `ads_catalog_update_product_set` for changes. An empty set is never used.
6. **Campaign, PAUSED.** `ads_catalog_list_dpa_eligible_catalogs` shows the catalog. `ads_create_campaign` with `objective` `OUTCOME_SALES` (the catalog link at campaign level per the tool's schema) → `ads_create_ad_set` as an Advantage+ catalog ad set with `promoted_object` `{product_set_id}` (plus the pixel and the purchase event per the schema), budget and schedule within the caps (rule 10) → `ads_create_ad` with an inline `object_story_spec` whose `template_data` carries the dynamic fields; **the exact field names of `template_data` and its placeholders are taken from `ads_get_field_context` at build time, never invented.** Everything PAUSED; rules 3–5 (inline creative, the feature opt-outs the schema accepts for a catalog ad, OPT_IN when anything is generated) and rule 8 (compliance) apply; the go rule is unchanged.
7. **Read back** (steps 5–7 of the standard sequence) and record.

**Deletes are the Owner's:** `ads_catalog_delete_product`, `ads_catalog_product_feed_delete`, `ads_catalog_product_set_delete` and `ads_catalog_product_feed_delete_rule` run only from the main session on the Owner's explicit word (`media-buyer` cannot call the first three).

**Weekly catalog health check** (in `/next-round` and `/health` while a catalog campaign exists; results with `as_of` in the plan and the campaign note): `ads_catalog_get_diagnostics` (MUST_FIX count must be 0; warnings listed); feed staleness (the last upload session in `ads_catalog_get_product_feed_upload_sessions` older than the schedule means a stale feed); product-set coverage (products per set from `ads_catalog_list_product_sets` against the catalog's total; a set that shrank or emptied); `ads_catalog_event_source_get_health` and `ads_catalog_get_dynamic_ads_health`.

**A poor catalog campaign is first a catalog problem.** Before touching creative, audience or budget, check in order: MUST_FIX diagnostics → a stale feed → event match between the pixel and the catalog → product-set coverage → prices and availability against the site. Only then the usual diagnosis order of `meta-performance-report`.

## Media uploads
- Default: `node creatives/tools/meta-upload.mjs <files...> [--title-prefix "<flight>"]` from the repo root; the account id comes from `META_AD_ACCOUNT_ID` in `.env`. Images → `image_hash` (Meta deduplicates by content, so re-uploading returns the existing hash); videos → `video_id` after the script has waited for `video_status` `ready` (about 30 s for a short clip; `--no-wait` skips the wait, and then `ads_get_ad_videos` must show `ready` before the ad is built). Results print as a table and land in `creatives/uploads/<date>-meta-upload.json`; copy them into the flight note's creatives table and the plan's media table with the date.
- `--check` first in a new session (prints the token holder, the account and read access, names only). `--dry-run <files>` lists what would go where without network.
- The token is `META_MARKETING_TOKEN` in the repo-root `.env`: a System User token with `ads_management` + `ads_read`, the Owner's to generate, rotate or revoke in Business Settings → System users. Never open, print or paste the value; never put it in a URL or a report. On code 190 (invalid token) or 200 (permissions) stop and report; the fix is the Owner's click.
- Fallback when the script cannot run: a public URL through `ads_creative_upload_media` (`upload_source` URL); when the fal MCP is loaded, its CDN can host the file (`mcp__fal__upload_file` prepare → curl PUT → `file_url`), which needs fal credits. `ads_creative_upload_local_image` is rolled out to some accounts only.
- Videos above 40 MB go through Meta's chunked start/transfer/finish protocol automatically (`--chunk-mb` changes the threshold). Keep upload files out of the preview site (it carries compressed copies only).

## Objectives and events per funnel type
Map each funnel in `config/product.md` to one row; confirm field names with `ads_get_field_context`.
| Funnel type | Objective | Optimization | Why |
|---|---|---|---|
| Website sign-up with no pixel event on success | OUTCOME_TRAFFIC | LANDING_PAGE_VIEWS until the product team ships a (consent-gated) result event | Without an event Meta cannot optimise for the result; switch to OUTCOME_LEADS once it fires |
| Website sign-up with a pixel `Lead` (or other standard) event | OUTCOME_LEADS on the pixel event | OFFSITE_CONVERSIONS, `custom_event_type` per the event | When the pixel fires only after consent, reported counts undercount |
| Instant form (lead ad) | OUTCOME_LEADS with an instant form on the company's Page | LEAD_GENERATION | Needs Lead Ads terms accepted and the lead delivery confirmed (Leads Center by default; the webhook steps only when `config/accounts.md` holds a `lead_webhook_url`; see "Lead-form ads"); instant-form buttons are APPLY_NOW, DOWNLOAD, GET_QUOTE, LEARN_MORE, SIGN_UP, SUBSCRIBE (expect CONTACT_US to be refused) |
| Tracker-free page (booking, contact) | OUTCOME_TRAFFIC | LANDING_PAGE_VIEWS | Results are counted in the app by `ref`, not by the pixel |
| Product catalog (e-commerce, a feed) | OUTCOME_SALES with the catalog and a product set | the purchase event, per the tool's schema | Only after the catalog order of work (see "Catalog and Advantage+ shopping campaigns"); a catalog with a MUST_FIX issue is not built on |
| Click-to-WhatsApp | messaging destination WhatsApp | conversations | The result is `messaging_conversation_started_7d`, counted only after the person sends the pre-filled message, with a reporting delay of up to a few hours |

## Destinations and link convention
Destinations are the URLs in the `config/product.md` destination pages table, matched to the ad's language. Never send paid traffic to a host or page that table marks as not for paid traffic (for example a sign-in screen).
`?ref=<prefix>-<yyyymm>-<audience>-<arm>-c<number>&utm_source=meta&utm_medium=paid_social&utm_campaign=<campaign_slug>&utm_content=creative<number>&utm_term=<arm>` on every link. The `ref` format and what reaches the database are in `config/accounts.md` (typically lower-case letters, digits, `_`, `-`, max 64 characters); the `utm_*` set is for analytics. Example `ref=mt-202611-buyers-a-c01`.

## Changing a live campaign
After every change below: re-read the object live, rewrite the campaign note's `## Current state` (with `as_of`), append to its `## Log`, update the flight note's creatives table when an ad was added, paused or deleted, and add a line to today's session note. A newly learned platform behaviour becomes a `memory/learnings/meta-platform/` note linked from `memory/maps/build.md` (per `memory-update`); a sub-agent such as `media-buyer` proposes it in `memory/inbox/proposals.md` instead and hands the ids back for the main session to record.
- Pause: `ads_update_entity` status PAUSED (free, no go needed; the harness pauses when the Owner asks in chat), then `ads_activate_entity` with that object id to apply the staged edit where the account stages edits.
- Schedule or name on live ad sets: update, then activate with `object_ids` of those ad sets. A campaign `spend_cap` (minor units) is a live scalar edit, on the Owner's go when it raises spend.
- New creative on a live ad set: create the ad, activate it alone with `object_ids` = that ad id. Old ads: pause, or DELETED on real objects; a draft ad under a live ad set cannot be set DELETED (error 1487839), PAUSED works; draft ad sets cannot be deleted (error 1487246); draft campaigns are discarded only in Ads Manager by the Owner.
- Budget: only on the Owner's go; +20 % per step, 48–72 h apart; never past a cap in `config/goals.md` (rule 10).
- A switch day (launch, destination change): a CTA or page that disappears on that day means the ad sets that point at it end on the schedule set at creation; the follow-up campaign is built PAUSED in advance as a separate campaign.

## Reads that mislead
- `last_7d` / `last_14d` / `last_30d` exclude today; a campaign that started today shows an empty row under them (use `today` or `maximum`).
- On WhatsApp ads `clicks` (all) includes Page-name and "see more" taps; `link_click` is the WhatsApp open.
- A campaign whose ad sets have different optimisation goals shows "Multiple conversions" or "—" as its campaign-level result.
- After approval and before first impressions, `delivery` reads `pending` / `preparing` and `ads_get_errors` stays empty: normal warm-up.
