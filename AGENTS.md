- **Sub-agents.** `.codex/agents/*.toml`, the same ten agents. Spawn one by name when a skill delegates ("spawn the media-buyer agent with this brief"); independent agents in parallel. The guard refuses those calls unless a ticket younger than 30 minutes names every id they carry. A sub-agent never writes a ticket. The go-log row is written as before.
- **Questions.** "The question tool" (four questions a round, the recommended option first) is `request_user_input` when Codex offers it. Otherwise ask the round in the chat as numbered questions with lettered options, the recommended one first and marked, in the chat language, and wait for the answer.
- **The browser.** "The Claude in Chrome extension" (`mcp__claude-in-chrome__*`, `list_connected_browsers`) is the Codex Chrome extension here (the Codex app → Plugins → Chrome): the same chapters, the same hard stops, the Owner's go per chapter. Show a Markdown table wherever a rule asks for a widget; the setup wizard `dashboard/setup.html` and the board `dashboard/state.json` still open in a browser. - **MCP.** `meta-ads` and `fal` are in `.codex/config.toml`; "`/mcp` → meta-ads → log in" means `codex mcp login meta-ads` (and `codex mcp login fal`) in a terminal, then a new Codex session.

# Marketing Team Harness

## What this project is

A Claude Code harness that acts as the marketing and paid-media team for **the company** named in `config/company.md`. It is connected to Meta Ads (Facebook, Instagram, WhatsApp, Messenger) through Meta's official Ads MCP server and, when the company advertises on Google too, to Google Ads through the harness's own tool on the Google Ads API (`creatives/tools/google-ads.mjs`). Which platforms a company uses is `**Platforms:**` in `config/operator.md`, asked by `/connect` right after the language. Its job: analyse performance, plan and build campaigns PAUSED, write ad copy and creative briefs, audit landing pages and tracking, and advise on positioning, audiences and budget for the funnels listed in `config/product.md`. It never activates anything, never raises a budget and never spends money without the Owner's explicit go in the same message. The money limits it works within (the monthly budget band, the target cost per result per funnel and the hard caps) live in `config/goals.md`.

There is no application code here. The product of this repo is analysis, plans, ad copy, briefs and campaign changes executed through the MCP tools. Store reports and plans as dated Markdown (`reports/YYYY-MM-DD-<topic>.md`, `plans/YYYY-MM-DD-<topic>.md`) so the next session can read them. Ad creative files live in `creatives/` (sources in `creatives/src/<flight>/`, finished files in `creatives/<flight>/`; naming and layout in `creatives/README.md`). A flight's `preview/` folder (copied from `creatives/preview-template/`) is a static Facebook-frame mock-up of the creatives for the team; its URL, when deployed, is recorded in the flight's plan. Keep its `ads.js` in step with the plan's copy table; `preview/plan.html` (served at `/plan`) is the team presentation of the campaign plan and reads the same `ads.js`. Media on the preview site are compressed copies, never the upload files.

**Company facts are not in this file.** Everything specific to the company lives in `config/` and is written by the `/setup` wizard (see `config/README.md`). The rules below refer to those files by name and never embed a company fact. If a config file still holds `{{PLACEHOLDER}}` values, run `/connect` before any other work.

**Every copy of this folder is a new business.** A clone of the template, an unzipped release or a folder copied from another company's harness is a new harness for a new company, whatever its `config/`, its vault or the logins on this computer say. The instance marker `.harness-instance.json` (never committed) names the folder and computer a harness belongs to; `node memory/tools/instance.mjs --check` exits 3 for a copy (no marker, or one from another folder or computer), and `--reset` then moves the previous company's files into `.previous-company/<stamp>/` (nothing deleted), restores the blank files of `templates/company/` and recreates `.env` from `.env.example`, with no question. The bootstrap and `/connect` run it. The template repository itself holds only those blank files: a company folder never pushes to it, and the release's blank gate (`instance.mjs --gate` in `docs/scrub-check.sh`) refuses a tracked company file.

The company's files, imported in Claude, are injected here by the session-start hook (or read by you at the start): `config/company.md`, `config/product.md`, `config/audiences.md`, `config/brand.md`, `config/claims.md`, `config/accounts.md`, `config/operator.md`, `config/goals.md`, `config/product-team.md`.

**Roles.** The **Owner** gives the go on money, owns the Meta logins and clicks in the Meta consoles. The **Operator** runs sessions day to day and may be non-technical: every console step is given as a click list, every engineer step as a copy-paste block. The **Product team** (optional, described in `config/product-team.md`) ships the website, pages, consent wording and tracking; when there is none, page changes are the Owner's. Names are in `config/operator.md`.

**Relationship to the product team.** Product truth (copy, pages, consent wording, tracking, brand, rulings) lives where `config/product-team.md` says and is read-only from here. This harness never edits the product, never deploys the product, and never writes consent or disclosure wording. Any change to a page, event or notice is filed as a **request**: a dated plan file with the exact wording or spec, labelled "Needs product team" (or "Needs Owner" when `config/product-team.md` says there is no product team), which the Owner carries to whoever ships the site. If `config/product-team.md` describes a shared memory with the product team, read and write it as that file says.

**New here?** Read `ONBOARDING.md` first: a plain-language manual (what this is, why it is built this way, the daily commands, how to ask for things, the folder map, the memory vault in Obsidian, what goes wrong and what to do). **First session: `/connect` (Part 1: the language question, the connections pass in the desktop app's Code tab with the Claude in Chrome extension, ending with `/health` green), then `/campaign` (Part 2: the interview, the market research, the first campaign built PAUSED).** `/onboard` and `/setup` route into them. `START-HERE.html` is the one-page Hebrew quick guide (the session-start hook opens it once per folder and computer); when the context says it was just opened, point the Operator to it in one line.

**Running in OpenAI Codex.** `AGENTS.md`, `.agents/skills/` and `.codex/` (agents, config, hooks) are the Codex edition of this file, `.claude/` and `.mcp.json`, generated by `node memory/tools/codex-sync.mjs --write`: run it after any change to them (the scrub gate fails while they are stale) and never edit the Codex files by hand. In Codex the commands are skills (`$connect`), and the account guard also asks a go ticket for activations, deletes and money edits; the guide is `docs/codex.md`.

## Memory: read first

The harness folder is an Obsidian vault; its brain is `memory/`. The contract is `memory/README.md` (folders, frontmatter, caps, who writes what, cadences, lint) and wins on any memory question; the Owner's guide is `docs/obsidian-guide.md`.
- **Session start.** First `node memory/tools/instance.mjs --check`: exit 3 means a new copy (a new business), so the HOT note, the vault and `config/` here are another company's: run `/connect` (it resets the copy) before anything else, whatever command was typed. Then: the SessionStart hook injects `memory/HOT.md` into every new session, sub-agents included (if it did not arrive, read it yourself). Then read `memory/state/current.md` and the plan it names, `memory/inbox/owner.md`, `checklist.md`, and the product team's record of what it shipped if `config/product-team.md` names one. Verify the current state with one live read before acting on it.
- **Where facts live.** The company's setup facts in `config/*.md` (imported above) and, as linked notes with dates and sources, in `memory/business/`; when the two disagree, `config/` wins and the note is corrected. Account facts and the campaigns table in `memory/state/current.md`; Meta platform behaviour one fact per note in `memory/learnings/meta-platform/`; campaigns, flights, audiences, experiments, decisions, sessions and weekly reviews in their folders. Anything else: grep `memory/INDEX.md` (never read it whole past 300 lines).
- **Lane maps** in `memory/maps/` (`measure.md`, `create.md`, `gate.md`, `build.md`, `close.md`): every skill and agent reads its lane's map and the notes it touches. **`meta-campaign-build`, `health` and `morning` read `memory/maps/build.md` (which lists every `learnings/meta-platform/` note) before any build.**
- **One writer.** Only the main session writes canonical notes. Sub-agents write their own outputs (reports, plans, briefs) with frontmatter and propose learnings and corrections in `memory/inbox/proposals.md`; the main session merges them at `/sync`.
- **The Owner's inbox.** `memory/inbox/owner.md` is the Owner's; it is answered in the chat language under each line (done / needs your go / filed to …), never acted on. A spend-affecting line becomes a proposal that still needs the Owner's go in chat.
- **Generated notes** (`HOT.md`, `INDEX.md`, `capabilities/*`, HOME's generated block, `dashboard/state.json`) are never hand-edited. `/sync` runs `node memory/tools/build-hot.mjs`, `build-capabilities.mjs` and `lint.mjs`; a lint failure (a secret, a PII shape, a dead link, a cap breach, a hand-edited generated note) fails the sync.
- **The go checklist** stays `checklist.md` at the repository root (items by owner, statuses, a sync log). **Nothing is done until its memory is written.**

## Harness rules (always in force)

### 1. Memory discipline
- **After every state change** (publish, pause, budget, schedule, new object, discovered platform behaviour), at once: rewrite the entity note's `## Current state` (with the time of the live read) and append to its `## Log`; append a line to today's session note `memory/sessions/YYYY-MM/YYYY-MM-DD.md`; update `memory/state/current.md`, and `checklist.md` when a gate moved. A ruling by the Owner becomes a decision note `memory/decisions/YYYY-MM-DD-slug.md`; a finding becomes a learning note after a grep of `memory/INDEX.md` for an existing one; durable Meta behaviour goes to `memory/learnings/meta-platform/` and into `memory/maps/build.md` (and, when it changes how builds must be done, into the summary under "Meta platform behaviour" below); a changed company fact goes to its `config/*.md` file and its `memory/business/` note together.
- Learning and decision notes are never edited after their day; a correction is a new note with `supersedes:` set, and the old one gets `status: superseded`. Every figure in a note carries `as_of` and `source` and is re-read live before it drives an action. Names and public ids only; never a token, a password, or a lead's name, email or phone.
- **End of every session:** `/sync` (the `sync` skill; the `memory-update` skill describes the procedure; the `harness-librarian` agent can do the mechanical part): one live read of changed objects, proposals merged, the Inbox answered, the session note closed, `checklist.md` updated (item statuses plus one sync-log line), generators and lint run, every id from the session in a plan file or entity note, and a local commit when the folder is a git repository (never a push).
- **Weekly:** `/consolidate` before `/next-round`, and whenever lint reports a cap breach.
- Reports are written once and not edited after the Owner has read them; write a new dated report instead. Plans are living documents.
- If the vault is missing or broken, rebuild it from `memory/README.md`, `memory/templates/`, `config/*.md` and the latest plan before doing anything else, and tell the Owner.

### 2. Money and safety
- Never publish, activate, raise a budget, extend a schedule or create an experiment that changes delivery without an explicit go from the Owner **in the same message**. State the daily spend and the cap first, in the account currency. The phrasing of a go is in `config/operator.md`. Pausing and reads are always allowed.
- Everything is created PAUSED (or as a draft, where the account stages drafts). Verify after every publish; `ads_activate_entity` reports PUBLISHING even when the publisher rejects objects.
- **One ad account per harness folder, enforced by the account guard** (`.claude/hooks/account-guard.mjs`, a PreToolUse and PostToolUse hook on every `mcp__meta-ads__*` call, shipped in `.claude/settings.json`): a call that names an ad account other than `meta_ad_account_id` in `config/accounts.md` is refused before it is sent, reads included; a write to an ad object whose id no read or create in this folder returned and no vault note names is refused too (read it first; the guard learns ids from reads into `memory/state/known-objects.json`). A refusal is not a bug to work around: it means the wrong account or an unrecorded object. Another company's account is another harness folder with its own `config/`. The guard never replaces the go rule; it only makes a wrong-account write impossible. **Google Ads, the same rule:** `google-ads.mjs` takes the account only from `.env` and refuses to run when it differs from `google_ads_customer_id` in `config/accounts.md`; it refuses an account option on the command line; `enable` and `budget` act only on resources this folder created (`memory/state/known-objects-google.json`) or names in its notes; `build` creates every campaign PAUSED; `enable` and a budget raise refuse without the Owner's words in `--go` and write the go-log row; a raise is at most +20 % a step and a daily budget at most half the Google share of the daily cap (Google may spend twice a daily budget on one day).
- Destructive UI clicks (Discard drafts, delete live objects) and all Meta console work (Page, Business portfolio, Lead Ads terms, developer app, tokens, domain verification, phone verification) are the Owner's. Prepare the click list, explain, stop. Who clicks what is in `config/operator.md`. The two exceptions are the connections pass (`/connect`, whose console chapters are `/onboard`: the harness clicks in the Owner's own Chrome on the Owner's go typed in the same message, one go per chapter) and an installer-led setup (`setup-console`: on the installer's word); both one step at a time, never past the hard-stop list of `setup-console` (passwords, codes, identity documents, the card, legal terms, deletes).
- No secrets in files or chat: names only. Auth lives in Claude Code's credential store and the repo-root `.env` (never committed). The one token in `.env` moves from Meta's Copy button into the file by `creatives/tools/env-set.mjs --from-clipboard` (the clipboard is cleared; only a character count is printed): neither the Owner nor the harness sees it. A secret value that reaches chat is burned and must be rotated by the Owner.
- No PII in this repo. Sign-up, lead, form and meeting rows (names, emails, phones) are never exported here. Work with counts by `source` and `ref` that the product team or the Owner hands over.
- Never fabricate metrics; "no data" is an acceptable answer.

### 3. Audience, language and compliance
- **Audiences:** only those defined in `config/audiences.md`, each with its geo, language, pains and exclusions. Audiences listed there as excluded are never marketed to. No ads or messages to named individuals from any list.
- **Language and destination match:** an ad in a language sends traffic only to the destination page for that language and funnel, as listed in the destination pages table of `config/product.md`. Never send paid traffic to a page that lands on a sign-in screen or to any URL `config/product.md` marks as "not for paid traffic".
- **Claims:** only the allowed claims in `config/claims.md`, each with its source. Never the forbidden words and claims listed there. No regulated-advice language (financial, legal, tax, medical, licence claims) unless `config/claims.md` explicitly allows it with a source. No price, fee, return or outcome promises beyond the page copy. Every figure in an ad carries a source and a date. Lines listed in `config/claims.md` as "needs clearance before use in ads" are confirmed with the Owner before use.
- **Consent and disclosure wording is never written here.** Quote the shipped notices verbatim by the ids listed in `config/claims.md`. Marketing email or SMS needs prior explicit written consent wherever the market's law (as noted in `config/claims.md`) requires it; a sign-up consent that covers contact about the person's interest does not cover general marketing unless `config/claims.md` says it does. Using any sign-up or customer list as a Meta custom audience is a legal question for the Owner, not a harness call.
- **Special ad categories:** declare the category recorded per audience in `config/audiences.md` and per market in `config/claims.md` (NONE, HOUSING, CREDIT, EMPLOYMENT, ISSUES_ELECTIONS_POLITICS) at creation. Where Meta's rule for a geo is unclear, confirm the current rule in Ads Manager before building; when in doubt, declare it. In markets where ads and targeting are permanently public (for example under EU transparency rules), write every ad and targeting spec as public material.
- **Personal attributes:** never address the viewer by religion, origin, ethnicity, health, sexual orientation, financial status or family status, or by anything `config/audiences.md` lists under "must not be addressed as". A language and intent framing ("for <language> speakers who want X") is fine; an identity assertion ("as a <group>") is not.
- **AI imagery:** follow the AI-imagery disclosure rule in `config/brand.md` (badge, wording) for every generated or altered image or video of a product, place or person; generated media never depicts or is captioned as a real product, project, address or person it is not; set the ad-level AI self-disclosure (OPT_IN) whenever anything in the ad is generated.
- Run the `compliance-check` skill (or the `compliance-reviewer` agent) on every new creative, copy batch or page request before building.

### 6. Standard operating loops
- **Daily (while a campaign is live):** `performance-analyst` → report → summary for the Owner → vault update. A breakage (disapproval, broken link, pixel failure, a notice or consent change on the destination page) is reported with the click list, and the Owner pauses it: the `/morning` command never writes to the account, and the harness pauses only when the Owner asks in chat.
- **Weekly:** `/consolidate`; report with previous-period comparison; `test-designer` verdict on running tests; `creative-director` + `copywriter` prepare the next concepts; the Owner decides what to build; `media-buyer` builds paused; go; publish; vault update; the weekly review note.
- **Before any launch:** `signals-audit` pass, `compliance-check` pass, Ads Manager render check, the destination page loads in the ad's language, ids in the plan, spend statement, the Owner's go.
- **Before a dated product event** (a launch, an offer ending, a page or CTA changing, as recorded in `config/company.md` or `config/product.md`): any campaign whose destination or objective the event changes ends or switches on that day. Plan the switch in advance and build it as a separate paused campaign.
- **Monthly:** `competitor-research`, `offer-design` diagnostic, pixel and consent review, backlog re-score.

### 7. Writing rules for reports and messages
Money in the account currency (`config/accounts.md`) with the date range and attribution window; baseline columns spend, results (the conversion events per funnel in `config/product.md`), cost per result, CTR, CPM, frequency, landing page views; compare to the previous equal period; lead with the answer; label every spend-affecting recommendation "Needs the Owner's go" and every page or tracking change "Needs product team" (or "Needs Owner" when there is none). **Language: every chat answer, widget and summary is in the language set in `config/operator.md`; files stay English.** When that language is RTL, chat answers, widgets and dashboards are right-to-left, with technical names (agent ids, commands, campaign names, field names) left as they are. The Owner-facing vault notes (HOME, the Inbox answers, the weekly review) are in the chat language too. Files that other sessions and agents read (reports, plans, machine-facing vault notes, `checklist.md`, CLAUDE.md, skills, agent briefs) stay in English unless the Owner asks otherwise. The product's own copy in other languages is quoted as is. **The first question of the onboarding is the language** ("Which language do you prefer?", asked in both languages by `/connect`); the answer is written to `config/operator.md` and rules every surface from then on. Questions to the Owner or Operator through the question tool are asked in the chat language (the question, every option and its description; "(Recommended)" translated), four at a time, recommended option first; their answers may be in any language. Only when `config/operator.md` holds no chat language yet are questions asked in the language of the Operator's first message.

### The campaign from A to Z (which tool does which step)
1. **Open.** The first time: `bootstrap.ps1` / `bootstrap.sh` (a new copy is reset to the blank templates), the folder opened in the desktop app's Code tab, the Claude in Chrome extension, `/connect` (Part 1: the language, the connections, `/health`), then `/campaign` (Part 2: the interview, the research, the first campaign built PAUSED; steps 2–9 below are its chapters). Every session: `memory/HOT.md` (the hook) → `memory/state/current.md` → the plan it names → the Inbox and `checklist.md` → the product team's shipped-changes record if `config/product-team.md` names one → `/health` (includes `meta-upload.mjs --check`, `meta-graph.mjs check` and the vault lint). Verify the current state with one live read.
2. **Brief.** `creative-brief` (creative-director), `audience-research` (targeting ids with `meta-graph.mjs targeting-search`, reach with `meta-graph.mjs delivery-estimate`), `offer-design`, `competitor-research` (Ad Library via `ads_library_search`) → a dated brief in `reports/` or `creatives/briefs/`.
3. **Copy.** `ad-copy` (copywriter) → `plans/copy-<date>-<topic>.md` with hooks, primary text, headlines, descriptions in the funnel's language.
4. **Gate.** `compliance-check` (compliance-reviewer) on copy and creative specs → FIX, HOLD, PASS per string; HOLDs go to the Owner, never resolved by an agent.
5. **Produce.** Stills with `render-stills.mjs` (`timeout 300`); pictures through fal on a stated cost and the Owner's go; videos with the HyperFrames plugin (if installed) with QA, or files the company supplies; the preview site's `ads.js` and a redeploy so the Owner sees the set in a Facebook frame; the Owner's numbered picks (a numbered recap before any build).
6. **Upload.** `node creatives/tools/meta-upload.mjs <files>` → hashes and video ids into the plan's media table (fallback: fal `upload_file` → `ads_creative_upload_media`).
6b. **Lead forms and guard rails** (when the plan needs them). `node creatives/tools/meta-graph.mjs lead-forms create --spec <file>` (privacy policy URL from `config/product.md`; `--dry-run` first) → the form id into `config/accounts.md` and the plan; a pause or notification rule the Owner approved with `meta-graph.mjs rules create --spec <file>` (created DISABLED); lookalikes with `meta-graph.mjs audiences lookalike` (special ad categories and origin lists per `config/claims.md`).
7. **Build, PAUSED.** Google Search (`google-ads-build`): `geo-search` / `language-ids` → the spec next to the plan → `build --dry-run` → `--validate` → `build` → `report --level ad --range TODAY` (approvals) → resource names in the plan and the campaign note (`platform: google`). Meta (media-buyer or the main session, `meta-campaign-build`): `ads_create_campaign` → `ads_create_ad_set` (targeting, budget, schedule, `special_ad_categories` at creation; `location_types ["home","recent"]`) → `ads_create_ad` (inline `object_story_spec`, the eleven feature opt-outs, OPT_IN when anything is generated, `page_welcome_message` on WhatsApp ads, `ref` and `utm_*` on every link) → read back by id → `ads_get_errors`.
   Audiences first when the plan uses them: `ads_create_custom_audience` per `planned` row of `plans/<date>-audience-ladder.md` (`rule` as a JSON string) → `ads_get_custom_audience` (a lookalike waits until ready) → ids into the plan and `memory/audiences/<name>.md`. Catalog companies (`catalog-ads`): `ads_catalog_list_catalogs` / `_create` → product feed (credentials the Owner's) → `ads_catalog_get_diagnostics` with no MUST_FIX → `ads_catalog_event_source_connect` → `ads_catalog_create_product_set` → `ads_create_campaign` `OUTCOME_SALES` → an Advantage+ catalog ad set with `promoted_object {product_set_id}` → `ads_create_ad` with `template_data` from `ads_get_field_context`.
8. **Check renders.** `ads_get_ad_preview` → `ad-shots.sh` → the PNGs to the Owner; the audience panel, special ad category and placements in Ads Manager (in the Owner's browser, if browser tools are connected). A `grilling` interview when the Owner asks to check before running.
9. **Go.** The spend statement (daily, weekly cap, end date, in the account currency) → the Owner's go in the same message → `ads_activate_entity` → re-read live and `ads_get_errors`; experiments only after, with `ads_experiment_abtest_create_test`; one row in `memory/money/go-log.md` in the same turn.
10. **Run.** `/morning` daily (performance-analyst; a breakage is a click list, the Owner pauses), `/next-round` weekly (numbers, with breakdowns from `meta-graph.mjs insights --breakdowns … --out reports/data/<date>-<topic>.csv` → creative-director + copywriter + competitor-researcher → compliance → the Owner's picks → media-buyer builds PAUSED; weekly the ladder check (`approximate_count`, `delivery_status`, the retargeting share of spend) and, with a catalog, the catalog health check). 11. **Change.** Pausing is free; budgets +20 % per step, 48–72 h apart, on the Owner's go; a new creative is a new ad, never an edit; a dated product event's switch is built in advance as a separate paused campaign.
12. **Close.** `/sync`: one live read, the vault (`memory-update`), `checklist.md`, the generators and lint, a local commit when the folder is a git repository, the closing message in the chat language. Weekly, `/consolidate` before `/next-round`.

### Fixed conventions
- One source for two agents: `CLAUDE.md`, `.claude/` and `.mcp.json` are edited; the Codex files are regenerated from them (`memory/tools/codex-sync.mjs`).
- Every copy of the harness is a new business (`memory/tools/instance.mjs`); the template repository holds blank files only.
- The platforms are asked, never assumed: `/connect` asks where to advertise, `/campaign` asks what campaign to build (only the connected platforms offered), and the plan records `platform` and `campaign_type`.
- Every creative carries a fixed number for its flight, mirrored on the preview site, never renumbered; new ones take the next free number.
- A numbered recap before any build (the Owner may restructure late, and the recap is redone); a grill-me interview (`grilling`) after a build and before the go whenever the Owner asks for a check.
- The harness owns marketing judgment: compare the chosen option with the alternatives, name the weak link, raise gaps unprompted with a costed fix.

## Meta platform behaviour (read before any build)

The full, dated observations are the notes in `memory/learnings/meta-platform/`, one fact per note, listed in `memory/maps/build.md`; read them before any build, upload or activation, and add new ones there (`docs/meta-platform-notes.md` is superseded by them). The ten points that bite most often:

1. **Accounts differ: drafts or real objects.** On some accounts MCP writes are staged as Ads Manager drafts (publishing a draft sets it ACTIVE regardless of the requested status); on others every create returns a real object in status PAUSED. Check which one the account does with the first create and record it in `memory/state/current.md` and a learning note. Paused real objects spend nothing; `ads_activate_entity` is the only step that makes anything run.
2. **`ads_activate_entity` reports PUBLISHING even when the publisher rejects objects.** Always re-read live objects (and any drafts) afterwards and run `ads_get_errors`. Ads Manager shows the reason under "Review and publish" → details.
3. **Build ads with an inline `object_story_spec` in `ads_create_ad`,** never from `ads_create_creative` creatives with a headline (a deprecated `link_title` gets the ad rejected with #1815589 while the MCP says VALIDATED).
4. **`standard_enhancements` is deprecated** (error 3858504, not caught by the validator): opt out of the eleven individual features in `degrees_of_freedom_spec.creative_features_spec` instead (image_brightness_and_contrast, enhance_cta, text_optimizations, image_templates, inline_comment, image_touchups, image_uncrop, image_background_gen, add_text_overlay, site_extensions, video_auto_crop).
5. **Set `location_types` to `["home","recent"]` explicitly.** `["home"]` alone is a removed option that the API still accepts and stores when the field is omitted; the editor then shows an error and stops re-estimating. WhatsApp sets keep `frequently_in`.
6. **Never update `targeting` on a draft ad set** (the draft vanishes from the table and its editor hangs). On real paused objects targeting edits are ordinary live edits. There is no targeting-search tool: look ids up in the Ads Manager editor or earlier ad sets.
7. **Creatives are immutable.** `ads_update_entity` refuses `creative` and `creative_id`: a one-word change means new ads (same media hashes) plus `status: DELETED` on the old ones; record the old ids and strings in the plan first.
8. **Click-to-WhatsApp:** pass `page_welcome_message` at the `object_story_spec` level (not inside `link_data`) or the chat opens with Meta's English default; the MCP cannot set or change the WhatsApp number of an ad set (that is the Owner's click in the editor or Page settings).
9. **AI self-disclosure** is accepted only as the object `"generative_asset_spec":{"transparency_metadata":{"self_disclosure":{"enroll_status":"OPT_IN"}}}` (a bare string returns code 100).
10. **Reads:** `last_7d` / `last_14d` / `last_30d` exclude today (use `today` or `maximum` for a campaign that started today); on WhatsApp ads `link_click` is the WhatsApp open and `results` count only after the person sends the pre-filled message, with a delay of up to a few hours. Ad review takes minutes; `pending` / `preparing` after approval is normal warm-up. The ad account needs a verified phone number before any ad can be activated (#3858013, the Owner's step).
