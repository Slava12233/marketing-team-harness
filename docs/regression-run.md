# Pre-release regression run (the maintainer's checklist)

Run this before every release, in order, and sign it off at the bottom. Buyers never run it. It exists because a skill edit, a tool change or a new rule can break the harness silently: nothing fails until a buyer's first build goes wrong.

**Where it runs.** Two places, never the maintainer's working repository:

- **The dry copy:** a scratch copy of the repository (outside it, for example a temp folder) with the fictional example company loaded, exactly as `examples/acme-fitness/README.md` "Loading it for a dry run" says. Its ids are fake, so every Meta read is refused or empty: that is the expected result, not a failure.
- **The demo copy:** a second scratch copy configured by `/setup` for a **demo ad account the maintainer owns** (its own Business portfolio, Page and ad account, a payment method, no real customers). Its `config/`, `.env` and vault never go into the repository. Live steps (7b, 7c, 8, 9) run only here, and nothing is ever activated: the demo account spends nothing.

**Time bounds.** Run every heavy command (test suites, evals, renders, the release) one at a time, in the foreground, with a time bound as the first word from Git Bash or a macOS shell with GNU coreutils (`timeout`, or `gtimeout` from `brew install coreutils`). Exit code 124 is the bound, not a red result: read the tail, stop any leftover `node` process (`tasklist` / `taskkill /PID <pid> /T /F` on Windows, `ps` / `kill` elsewhere), then run once more with fewer files and record the result as partial. Never loop a command hoping for another result.

## Running the skill evals

The evals use the format of Anthropic's `skill-creator` skill (`references/schemas.md` in that skill, section `evals.json`): each covered skill has `.claude/skills/<skill>/evals/evals.json` with `skill_name` and a list of `evals`, each with `id`, `prompt`, `expected_output`, `files` (input files, paths relative to the skill folder, all under `evals/files/`, fictional, ids like `100000000000001`) and `expectations` (the assertions the grader checks against the transcript and the outputs). Two extra fields, `name` and `rationale`, are this harness's: `name` is the eval's directory name, `rationale` says why the case exists. The prompts are dry runs: they need no Meta account and every assertion can be judged from the transcript and the `outputs/` folder.

`skill-creator` has no command-line runner for these evals (its `scripts/run_eval.py` only tests whether a description triggers the skill). The run is driven by the skill itself, in a Claude Code session with the `skill-creator` plugin enabled, opened in the dry copy:

1. Ask: "Use skill-creator to run the evals in `.claude/skills/<skill>/evals/evals.json` against the current skill, with-skill runs only, workspace in `<scratch>/<skill>-workspace/` (outside this folder)". It spawns one run per eval with the skill and the eval's input files, saves each run's outputs under `<workspace>/iteration-1/eval-<name>/with_skill/outputs/` with an `eval_metadata.json`, and grades each run with its grader agent into `grading.json` (fields `text`, `passed`, `evidence`).
2. Aggregate, from the `skill-creator` skill's own folder (Python 3, the maintainer's machine only): `timeout 300 python -m scripts.aggregate_benchmark <workspace>/iteration-1 --skill-name <skill>`, which writes `benchmark.json` and `benchmark.md`.
3. Optional viewer: `timeout 300 python eval-viewer/generate_review.py <workspace>/iteration-1 --skill-name <skill> --benchmark <workspace>/iteration-1/benchmark.json --static <scratch>/<skill>-review.html`.
4. Delete the workspace afterwards. Keep it out of the repository: a workspace inside `.claude/skills/` dirties the tree and the release refuses.

If your Claude Code version offers its own plugin or skill eval command, check what format it reads before using it on these files (not verified here).
